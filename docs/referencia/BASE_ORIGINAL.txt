# 1. PROYECTO

Nombre:

**Voluntia — Plataforma de gestión de voluntariado y actividades de impacto social**

Voluntia es una plataforma destinada a conectar voluntarios con organizaciones que realizan actividades de beneficio social.

El sistema debe permitir gestionar:

- cuentas de usuario;
- roles;
- perfiles de voluntarios;
- organizaciones;
- miembros de organizaciones;
- verificación de organizaciones;
- categorías sociales;
- habilidades;
- actividades de voluntariado;
- requisitos de habilidades;
- inscripciones;
- historial de estados;
- asistencia;
- favoritos;
- resultados e impacto;
- evidencias;
- certificados;
- valoraciones;
- notificaciones;
- conversaciones;
- mensajes;
- auditoría de acciones.

# 3. TABLAS

## USUARIO

Representa una cuenta del sistema.

Campos:

- id_usuario — PK
- correo — UNIQUE, NOT NULL
- clave_hash — NOT NULL
- email_verificado
- estado
- fecha_registro
- ultimo_acceso
- fecha_actualizacion

La contraseña nunca debe almacenarse directamente. Se debe almacenar únicamente su hash.

---

## ROL

Define los diferentes roles disponibles.

Campos:

- id_rol — PK
- nombre — UNIQUE, NOT NULL
- descripcion

Posibles roles:

- Administrador
- Voluntario
- Organización
- Moderador

---

## USUARIO_ROL

Resuelve la relación muchos a muchos entre USUARIO y ROL.

Campos:

- id_usuario — PK, FK → USUARIO
- id_rol — PK, FK → ROL
- fecha_asignacion
- activo

Clave primaria compuesta:

(id_usuario, id_rol)

Un usuario puede poseer uno o varios roles.

---

## TOKEN_CUENTA

Gestiona tokens relacionados con funciones de seguridad.

Campos:

# 5. NORMALIZACIÓN

El modelo debe mantenerse normalizado como mínimo hasta 3FN.

## Primera Forma Normal — 1FN

Todos los atributos deben contener valores atómicos.

No almacenar:

habilidades = "Cocina, Logística, Primeros auxilios"

Se utiliza:

VOLUNTARIO_HABILIDAD.

Tampoco almacenar varios roles en una sola columna.

Se utiliza:

USUARIO_ROL.

---

## Segunda Forma Normal — 2FN

Todos los atributos que no forman parte de una clave deben depender de la clave completa.

Las relaciones N:M utilizan tablas puente independientes, por ejemplo:

- USUARIO_ROL
- VOLUNTARIO_HABILIDAD
- ACTIVIDAD_HABILIDAD
- ORGANIZACION_MIEMBRO
- ORGANIZACION_CATEGORIA
- FAVORITO

Los atributos de las entidades no se mezclan dentro de estas relaciones.

---

## Tercera Forma Normal — 3FN

No deben existir dependencias transitivas entre atributos no clave.

Por ejemplo, ACTIVIDAD no almacena:

- nombre_organizacion;
- teléfono_organizacion;
- nombre_categoria;
- nombre_habilidad.

Solo almacena las claves foráneas correspondientes:

- id_organizacion;
- id_categoria;
- id_ubicacion.

Los datos completos permanecen en las tablas respectivas.

# 6. REGLAS IMPORTANTES

1. Los correos de usuario deben ser únicos.

2. Las contraseñas deben almacenarse mediante hash.

3. Un usuario puede tener múltiples roles.

4. Un usuario puede pertenecer a varias organizaciones.

5. Una organización puede tener varios miembros.

6. Una organización puede trabajar en varias categorías.

7. Un voluntario puede tener múltiples habilidades.

8. Una actividad puede requerir múltiples habilidades.

9. Un voluntario no puede inscribirse dos veces en una misma actividad.

10. Una inscripción conserva su historial de estados.

11. Solo puede existir un registro de asistencia por inscripción.

12. Solo puede existir un certificado por inscripción.

13. Solo puede existir una valoración por inscripción.

14. Los archivos e imágenes deben almacenarse fuera de la BD y registrar solamente sus URLs o referencias.

15. Las acciones relevantes deben poder registrarse en la bitácora.

16. Las claves foráneas deben garantizar la integridad referencial.

17. El diseño debe permitir ampliar funcionalidades sin modificar innecesariamente las tablas centrales.
